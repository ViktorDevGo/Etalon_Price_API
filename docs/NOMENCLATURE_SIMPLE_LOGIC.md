# Упрощенная логика загрузки номенклатуры

## Обзор

С **миграции 015** система использует упрощенную логику проверки дублей при загрузке номенклатуры.

### Принцип работы

**Проверка только по артикулу (CAE):**
- ✅ Артикул уже есть в БД → **пропускаем** (skip)
- ✅ Артикул новый → **добавляем** новую строку

### Отличие от предыдущей логики

| Аспект | Старая логика | Новая логика |
|--------|---------------|--------------|
| **Проверка дублей** | По ВСЕМ полям (14 полей) | Только по CAE |
| **История изменений** | ✅ Хранится (создавались версии) | ❌ Не хранится |
| **Обновление данных** | Создавалась новая версия | Данные НЕ обновляются |
| **UNIQUE constraint** | ❌ Нет | ✅ Есть на cae |

### Технические детали

#### 1. База данных

**UNIQUE constraint:**
```sql
ALTER TABLE nomenclature_tyres
ADD CONSTRAINT nomenclature_tyres_cae_unique UNIQUE (cae);

ALTER TABLE nomenclature_rims
ADD CONSTRAINT nomenclature_rims_cae_unique UNIQUE (cae);
```

**Миграция:** `migrations/015_add_unique_constraint_cae.sql`

#### 2. Код репозитория

**Проверка дублей (nomenclature_repository.go):**
```sql
-- Вместо проверки всех полей:
WHERE NOT EXISTS (
    SELECT 1
    FROM nomenclature_tyres nt
    WHERE nt.cae = t.cae
      AND nt.name = t.name
      AND ... -- еще 12 полей
)

-- Теперь проверяем только CAE:
WHERE NOT EXISTS (
    SELECT 1
    FROM nomenclature_tyres nt
    WHERE nt.cae = t.cae
)
```

#### 3. Поведение при синхронизации

**Первая загрузка:**
```
Загружено из XML: 53,969 записей
Новых: 53,969
Пропущено: 0
```

**Повторная загрузка (те же данные):**
```
Загружено из XML: 53,969 записей
Новых: 0
Пропущено: 53,969 (все дубли по CAE)
```

**Загрузка с новыми артикулами:**
```
Загружено из XML: 54,500 записей
Новых: 531 (новые CAE)
Пропущено: 53,969 (существующие CAE)
```

### Преимущества новой логики

1. **Производительность:**
   - Быстрее проверка (1 поле вместо 14)
   - Меньше нагрузка на БД

2. **Простота:**
   - Понятное правило: 1 CAE = 1 запись
   - Нет версионирования, нет истории

3. **Надежность:**
   - UNIQUE constraint на уровне БД
   - Невозможно создать дубль программно

4. **Предсказуемость:**
   - Данные не изменяются автоматически
   - Полный контроль над обновлениями

### Ограничения

1. **Нет истории изменений:**
   - Если данные изменились у поставщика, изменения НЕ попадут в БД
   - Нужно вручную обновлять или удалять старые записи

2. **Нет автообновления:**
   - Изменения цен, названий, параметров НЕ применяются
   - Требуется ручное управление обновлениями

### Когда нужно обновить данные

**Вариант 1: Полная перезагрузка (рекомендуется)**
```bash
# 1. Очистить таблицу
psql -c "TRUNCATE TABLE nomenclature_tyres CASCADE;"

# 2. Загрузить заново
go run cmd/sync-nomenclature/main.go -type=tyres
```

**Вариант 2: Обновление конкретных записей**
```sql
-- Удалить старые версии конкретных артикулов
DELETE FROM nomenclature_tyres WHERE cae IN ('артикул1', 'артикул2');

-- Запустить синхронизацию - новые данные загрузятся
```

**Вариант 3: Использовать ON CONFLICT (будущее улучшение)**
```sql
INSERT INTO nomenclature_tyres (...)
VALUES (...)
ON CONFLICT (cae) DO UPDATE SET
    name = EXCLUDED.name,
    price = EXCLUDED.price,
    ...
```

### Миграция с предыдущей логики

При применении миграции 015:
1. ✅ Автоматически удаляются старые версии (оставляется последняя)
2. ✅ Добавляется UNIQUE constraint на cae
3. ✅ Новая логика проверки применяется сразу

### Проверка работы

**Тест 1: Проверить UNIQUE constraint**
```sql
-- Должна быть ошибка:
INSERT INTO nomenclature_tyres (cae, name, ...)
VALUES ('000202', 'Test', ...);
-- ERROR: duplicate key value violates unique constraint "nomenclature_tyres_cae_unique"
```

**Тест 2: Повторная синхронизация**
```bash
go run cmd/sync-nomenclature/main.go -type=tyres
# Ожидается: new=0, skipped_duplicates=53969
```

**Тест 3: Количество записей**
```sql
SELECT COUNT(*), COUNT(DISTINCT cae) FROM nomenclature_tyres;
-- Должны совпадать (нет дублей)
```
